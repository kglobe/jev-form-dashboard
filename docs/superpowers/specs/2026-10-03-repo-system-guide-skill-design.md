# 從程式碼與文件產製互動式系統指南：Skill 規格

日期：2026-10-03  
狀態：待實作。這份文件定義未來的 Skill；本次不建立或安裝 Skill。

## 1. 目的

使用者指定專案文件或要說明的系統範圍後，Skill 產出一份**可獨立開啟的 HTML 技術指南**。讀者應能先看懂怎麼使用系統、誰負責關鍵決策，再查看互動架構圖、資料流程、規則、失敗行為及程式碼來源。

這次的 JEV 儀表板指南是驗收範例。未來的 Skill 不內建 JEV 的題目名稱、欄位上限、圖型或信心門檻；這些事實每次都要從目標專案取得。

## 2. 適用範圍

建議名稱：`repo-system-guide`。

建議觸發描述：使用者要求根據現有儲存庫、設計文件或兩者，製作說明「系統架構＋實際操作＋內部流程」的單檔 HTML 指南時使用。只有畫一張圖、只轉換 Markdown 格式、只寫 README，或要求發佈網站時，不由這個 Skill 接手整個工作。

必要輸入是要說明的系統或流程，以及至少一項可讀來源（儲存庫、文件或使用者提供的規格）。使用者可指定讀者、輸出路徑、語言與要強調的情境。未指定讀者或語言時，依專案現有文件與對話語言判斷；未指定輸出路徑時，放在來源文件旁或儲存庫的 `docs/`。

範例請求：

> 用 `$repo-system-guide` 讀 `docs/JEV智慧化產製儀表板的流程與方法.md` 和目前程式碼，做一份介紹操作、兩輪分析與系統架構的單檔 HTML。

## 3. 交付物

主要交付物是一個 HTML 檔案，須內嵌樣式、必要的互動程式與圖表內容。搬到另一台電腦後，讀者不靠產生腳本或網路資源，也能閱讀主要內容並操作架構圖。

產生腳本、Archify 候選 JSON、驗證紀錄可放在 HTML 旁的支援資料夾，供日後修改。支援檔案不是讀者開啟指南的前提。使用者指定輸出位置時，依指定位置交付，不另外留下名稱相近、容易混淆的最終版。

HTML 的資訊順序：

1. 首屏說清楚系統用途、讀者下一步，以及最重要的責任分工。
2. 給出可照做的操作路徑；需要設定或權限時寫明前提。
3. 用一個**有來源依據的具體例子**走過主要資料流，標明哪些結果取決於執行時資料或外部回答。
4. 放互動架構圖與完整技術說明；以目錄連到流程、規則、資料邊界、失敗行為和限制。
5. 讓關鍵主張可回查來源文件或程式碼；清楚區分目前已實作、設計中與未知的內容。

章節數與版面不固定。沒有真實範例資料時，使用者可提供例子；否則用標明「示意」的最小例子，不能把示意結果寫成系統實測結果。

## 4. 來源與正確性

### 4.1 讀取順序

先讀使用者指定的文件、專案指示與入口點，再沿實際呼叫路徑查所需程式碼。只追查能改變本次說明的分支、規則與外部依賴。記錄儲存庫 revision；工作目錄有未提交變更時，辨別證據來自提交版本或目前工作樹。

程式碼決定「目前如何運作」；文件提供背景、用語與設計理由。若兩者衝突，指南明寫差異並以已查到的實作描述現況。除非使用者也要求修文件，Skill 不默默改動來源文件。文件只有設計、沒有實作證據時，標成設計內容。

### 4.2 主張與隱私

每個主要元件、跨邊界連線及會改變結果的條件，都要有對應來源。圖中的來源標記不能只指向啟動檔或無關的呼叫端。無法查證的細節直接寫「待確認」，不捏造部署架構、數字或安全承諾。

產生內容前檢查機敏資料。金鑰、密碼、實際客戶資料列與未授權的內部網址不得進入 HTML 或圖表候選稿。範例值須為公開或明確標示的示意資料。來源連結不得包含憑證。

## 5. 產生流程

1. **界定問題**：列出讀者要完成的操作、要理解的主要流程，以及必須呈現的例外。把未回答但會影響事實的問題列出；能從程式碼解決的先查證。
2. **建立內容骨架**：先寫操作路徑、責任分工與一個具體例子，再把較細的規則放進可跳轉的章節。保留原文件的必要資訊；長篇 Markdown 直接包進 HTML，不算完成指南。
3. **產生架構圖**：有程式碼時依實際元件與呼叫關係製圖。若可用 `archify`，依其 Skill 的 schema、來源證據與 `finalize` 流程產生圖；只在工具回報通過後宣稱圖通過驗證。圖需呈現主線和會改變行為的必要支線，細節留在正文。
4. **組成單檔 HTML**：把已驗證的圖以內嵌方式放入文件，建立章節目錄、程式碼區塊與可橫向捲動的表格。中文採台灣用語；若目標專案要求 `humanizer-zh`，在交付前依其流程校對文字。
5. **驗收與交付**：開啟最終檔案，檢查桌面及手機寬度、目錄錨點、圖表載入、橫向溢出與瀏覽器錯誤。最後只連到通過檢查的 HTML，並分開說明圖的自動驗證與人工視覺檢查結果。

Skill 只定義這些決策與驗收點。Markdown 轉換、目錄產生與圖表內嵌若反覆使用，可放進小型產生腳本；視覺樣式可獨立放在資產檔。不要把本專案的 15 個章節、固定欄寬或某一種配色寫成跨專案規則。

## 6. 完成條件

以下項目都要有實際檢查結果，不能只憑檔案存在就宣稱完成：

| 項目 | 驗收方式 |
|---|---|
| 操作與分析可讀 | 不看原始碼也能找到「怎麼用」「系統怎麼判斷」「誰決定最後結果」；例子不把可能結果說成必然結果 |
| 來源正確 | 關鍵流程和條件有相符來源；已實作與規劃內容分開；文件與程式碼衝突已標明 |
| 架構圖 | 依所用製圖工具的完整驗證流程通過；未通過時保留診斷，不宣稱成功 |
| 單檔交付 | 最終 HTML 離線可開啟，互動圖、樣式和正文不依賴支援資料夾 |
| 瀏覽器 | 至少檢查桌面 1440px 與手機 390px：圖可載入、目錄連結可達、沒有頁面橫向溢出或未處理的執行錯誤 |

若某個瀏覽器或來源驗證環境不可用，仍可交付已產生的檔案，但要列出未通過或未執行的項目，不把它寫成已驗收。

## 7. Skill 實作時的最小檔案配置

```text
repo-system-guide/
├── SKILL.md                  # 觸發條件、來源規則、主要流程、完成條件
└── scripts/build_guide.py    # 只有在單檔組裝邏輯確實重複時才保留
```

`SKILL.md` 應短而能判斷何時適用。Archify 的 schema 與驗證細節由 Archify Skill 維護，這個 Skill 只說何時呼叫及如何使用其驗證結果。若實作需要大量版面規則，再拆到 `references/` 或 `assets/`，不要先建立空資料夾。

## 8. 後續 Skill 測試情境

1. **JEV 儀表板**：指定本專案文件與程式碼。結果應有操作、兩輪分析、後端合法性檢查、載入後異常支線；不能把 JEV 畫成直接產生圖表資料。
2. **文件與程式碼衝突**：文件寫舊的重試時間，程式碼有新門檻。結果須描述目前程式碼行為並標出差異，不靜默複製舊數字。
3. **只有文件的專案**：可以產生標明「依文件」的流程圖與指南，不得偽造程式碼來源或說已驗證實作。
4. **缺少瀏覽器或 Archify**：保留能完成的產物與診斷，明確回報未執行的驗證；不得把部分成功寫成全部通過。

這些情境用來驗證代理是否能依 Skill 正確判斷。實作 Skill 時再建立測試素材與 `SKILL.md`，不在本規格階段先寫空殼。
