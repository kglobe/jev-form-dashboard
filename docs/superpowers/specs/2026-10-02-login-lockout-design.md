# JEV 儀表板：登入失敗次數限制（設計）

日期：2026-10-02
前提：登入的規則見 [唯讀分享 spec](2026-10-01-auth-sharing-design.md)，本文件只寫這次改變的部分。

## 1. 問題

帳密登入沒有次數限制，同一個帳號的密碼可以一直猜（backlog「正式上線前」P2）。唯讀分享 spec 第 10 節當時把這件事列為不做。

## 2. 規則

### 2.1 怎麼算

- 每個帳號分開算。帳號名稱先照唯讀分享 spec 2.1 轉換（去掉前後空白、轉小寫），所以 `U1` 和 ` u1 ` 算同一個帳號。
- 密碼連續錯 5 次，這個帳號鎖 15 分鐘。5 次和 15 分鐘寫死在 `LoginLockout`，不做成設定。
- 比對密碼之前先占一次名額，比對完才知道對錯。同時送再多請求，也只有 5 次會真的比對密碼，其他的直接擋下。
- 第 5 次一占下去就開始鎖，這次密碼對了才解開。所以第 5 次還在比對的時候，同一個帳號的其他請求會先拿到 429。
- 密碼對了就從 0 重新算，鎖過期之後也從 0 重新算。

### 2.2 鎖住的時候

- 用密碼登入一律回 429 `{"error":"登入失敗太多次，請 N 分鐘後再試"}`，不比對密碼，密碼對了也一樣。
- N 是剩下的時間換算成分鐘，無條件進位，最少是 1。剛鎖住是 15，剩 14 分 30 秒也是 15，剩 1 秒是 1。
- 單一登入（OIDC）不受影響，鎖住的帳號照樣能用單一登入。

### 2.3 哪些帳號會算

- 只算資料庫查得到、而且有密碼的帳號，記憶體裡的筆數不會超過帳號數。
- 沒有這個帳號，或帳號只用單一登入（沒有密碼）：照舊回 401「帳號或密碼錯誤」，不會被鎖。
- 停用的帳號也會算。密碼錯照舊回「帳號或密碼錯誤」，密碼對照舊回「帳號已停用，請聯絡管理員」，密碼對了一樣從 0 重新算。錯滿 5 次就跟其他帳號一樣回 429。
- 取捨：429 等於告訴對方「這個帳號存在，而且有密碼」，跟唯讀分享 spec 2.2「不透露帳號存不存在」不一致。這是內部系統，我們接受：帳號名稱本來就不是秘密，分享對話框就是直接輸入對方的帳號名稱；被鎖的人也看得懂自己為什麼登不進去。真的要藏，就得連不存在的帳號也記次數，記憶體就沒有上限了。

### 2.4 解鎖

- 等 15 分鐘。
- 管理員在「帳號管理」幫他設定或重設密碼（`PUT /api/admin/accounts/{username}/password`），鎖馬上解開。管理員就用這個方法解鎖，不另外做「解鎖」按鈕。
- 後端重啟會清掉所有的鎖（2.6）。

### 2.5 log

- 帳號鎖住時寫一行 WARN：「帳號「u1」密碼連續錯了 5 次，鎖住 15 分鐘」。只寫帳號名稱，不寫密碼。鎖住期間被擋下來的請求不再寫。

### 2.6 存在哪裡

- 存在後端的記憶體，跟工作階段一樣（唯讀分享 spec 2.2），後端重啟就清掉。
- `ponytail:` 只有一台後端時才準。要跑多台後端時，跟 Spring Session JDBC 一起搬到資料庫。
- `ponytail:` 整張計數表共用一把鎖，鎖住的範圍只有幾個 map 操作。登入多到在這裡排隊時，再改成每個帳號一把。

## 3. API

`POST /api/auth/login` 多一種回應：429 `{"error":"登入失敗太多次，請 N 分鐘後再試"}`。跟其他登入錯誤一樣由 `SecurityConfig.writeError` 寫出，Content-Type 是 `application/json;charset=UTF-8`。

其他回應不變（唯讀分享 spec 4.1）。

## 4. 後端

- 新增 `LoginLockout`（`auth` 套件，`@Component`）：
  - `check(username, passwordCheck)`：先占一次名額，鎖住時丟 Spring 的 `LockedException`，訊息就是 2.2 那句。接著跑 `passwordCheck`：丟出 `BadCredentialsException` 時，這次剛好是第 5 次就寫 WARN；沒丟例外就清掉計數。
  - `clear(username)`：清掉計數。
- `SecurityConfig.passwordLogin`：`DaoAuthenticationProvider` 改成匿名子類別，覆寫比對密碼的 `additionalAuthenticationChecks`，包在 `lockout.check` 裡面。這一步在查到帳號之後，找不到的帳號、只用單一登入的帳號都到不了這裡（2.3）。停用的檢查還是在比對之後（`postAuthenticationChecks`），不受影響。
- `failureHandler`：`LockedException` 回 429，訊息用例外帶的訊息。`LockedException` 是 `AccountStatusException`，`ProviderManager` 會直接往外丟，不會再試別的 provider。
- `AccountService.resetPassword`：寫入新密碼之後呼叫 `lockout.clear`（2.4）。自己改密碼（`changeOwnPassword`）不用清，會用到這支的人已經登入了。
- 時間從既有的 `Clock` bean（`JevConfig.clock()`）讀。測試把它換成 mock，就能直接跳過 15 分鐘，不用 sleep。
- 單一登入的程式沒動。

## 5. 畫面

程式不用改。`api.js` 只特別處理 401，其他狀態碼都把後端的 `error` 原樣丟出來（唯讀分享 spec 7.10）。登入頁和重新登入對話框共用的 `LoginForm` 會直接顯示「登入失敗太多次，請 N 分鐘後再試」，表單留著，時間到了可以再試。這次補上測試，確認訊息不會被換成別的字。

## 6. 測試

後端（`LoginLockoutTest`，`Clock` 換成 mock，所以另開一個 context）：

- 密碼錯 5 次，第 6 次用對的密碼也回 429「請 15 分鐘後再試」；過了 30 秒還是 15；另一個帳號照常登入。
- 鎖了 14 分 59 秒時是「請 1 分鐘後再試」；滿 15 分鐘，用對的密碼回 204。
- 鎖過期後從 0 重新算：再錯 5 次又鎖住。
- 錯 4 次後登入成功，再錯 4 次照樣登得進去。
- 同時 20 個：直接呼叫 `LoginLockout.check`，讓比對密碼那一段卡住，等 20 個都到了才放行，只有 5 個真的進到比對。這一項不透過 MockMvc 測，因為 MockMvc 同時送的請求實際上是一個接一個跑完，「比對完才記次數」的錯誤寫法照樣會通過。
- 管理員重設密碼後，鎖住的帳號馬上能用新密碼登入。
- 不存在的帳號、只用單一登入的帳號，錯 10 次還是 401「帳號或密碼錯誤」。
- 帳號名稱先轉換再算：` U1 ` 錯 3 次、`u1` 錯 2 次，`U1` 就被鎖了。
- 停用的帳號：錯 4 次後用對的密碼，還是「帳號已停用，請聯絡管理員」，而且從 0 重新算，再錯 4 次也不會鎖。
- 鎖住時只寫一行 WARN，log 裡沒有密碼。

前端：

- `api.test.js`：login 回 429 時不呼叫 `onUnauthorized`，訊息照後端，`status` 是 429。
- 登入頁、重新登入對話框：`login` 回 429 時顯示後端的訊息，「登入」還能按；重新登入對話框不打 `me`，也不關掉。

瀏覽器（Chrome，主 session 做）：

1. 用測試帳號連續輸錯 5 次密碼，每次都是「帳號或密碼錯誤」。
2. 第 6 次輸入正確的密碼，看到「登入失敗太多次，請 15 分鐘後再試」。
3. 管理員在「帳號管理」幫他重設密碼，用新密碼登得進去。

## 7. 決定（2026-10-02）

| 題目 | 選擇 | 沒選的 |
|---|---|---|
| 怎麼算 | 每個帳號分開算，連續錯 5 次鎖 15 分鐘，寫死 | 依 IP 算；做成設定 |
| 鎖住時 | 429，不比對密碼，對的密碼也擋 | 照樣比對，密碼對就放行 |
| 同時送很多個 | 比對密碼前先占名額，第 5 次一占下去就鎖，這次對了才解開 | 比對完才記次數（同時送的請求都能猜） |
| 剩幾分鐘 | 無條件進位，最少 1 | 四捨五入；顯示到秒 |
| 哪些帳號會算 | 只算查得到、有密碼的帳號 | 所有輸入過的名稱（記憶體沒有上限） |
| 透露帳號存在 | 接受，內部系統 | 不存在的帳號也回 429 |
| 停用的帳號輸對密碼 | 照舊說「已停用」，從 0 重新算（密碼對就不算失敗） | 不重新算（停用的人輸對 5 次也會被鎖） |
| 存在哪裡 | 記憶體，重啟清掉 | 資料庫（多台後端時再搬） |
| 管理員怎麼解鎖 | 重設密碼時一起解開 | 另外做「解鎖」按鈕 |
| log | 鎖住時寫一行 WARN，只寫帳號 | 每次失敗都寫 |
| 時間來源 | 既有的 `Clock` bean | 另外宣告一個 |
| 同時送的測試 | 直接打 `LoginLockout`，讓比對卡住 | 透過 MockMvc 同時送（抓不到錯誤寫法） |
