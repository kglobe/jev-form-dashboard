# JEV 儀表板：儀表板自動更新（設計）

日期：2026-10-07

前提：[多來源 spec](2026-09-27-multi-source-dashboard-design.md)、[登入與唯讀分享 spec](2026-10-01-auth-sharing-design.md)（下稱「分享 spec」）、[儀表板篩選器 spec](2026-10-07-dashboard-filters-design.md)（下稱「篩選器 spec」）。本文件只寫這次改變的部分。

## 1. 問題

打開儀表板時，`/data` 和 `/highlight` 各打一次，之後就不會再抓。外部 API 來源的資料變了，或有人按了「更新資料」，畫面都不會跟著變，只能重新整理頁面，而重新整理會把臨時改的篩選打回預設。畫面上也看不出資料是什麼時候抓的。

這次做的是 backlog「補齊」P3「自動重新整理與輪播」的前半段，2026-10-07 使用者把它調到 P2：每份儀表板可以設定自己的更新間隔，畫面上顯示最後更新時間（參考 Grafana 的 refresh）。

## 2. 規則

### 2.1 更新間隔

- 每份儀表板一個設定，選項是「不自動更新、每 1 分鐘、每 5 分鐘、每 10 分鐘、每 15 分鐘」。新建立的儀表板是「不自動更新」。
- 只有擁有者能改，改了馬上存檔，不用另外按儲存。
- 被分享的人和沒登入的訪客照擁有者的設定自動更新，不能改，也不能關掉。
- 最長只到 15 分鐘，原因是登入的工作階段閒置 30 分鐘就過期（Spring Boot 預設 `server.servlet.session.timeout`）。間隔設 30 或 60 分鐘的話，下一次自動更新時，登入的人的工作階段可能已經過期，畫面會跳出「登入逾時」。15 分鐘以內，每次更新都會讓工作階段保持有效。

### 2.2 怎麼更新

- 時間到了，照目前的篩選（包括臨時改的，篩選器 spec 2.3）重打 `/data`，再打 `/highlight`，跟改篩選時一樣。
- 下一次更新從上一次成功抓到資料的時間開始算。改篩選也算抓了一次，計時重新開始。
- 擁有者改了間隔，從改的那一刻重新計時。
- 更新時卡片留著舊的資料和異常標註，新的回來再換，不閃「載入中」（多來源 spec 10.3）。
  - 跟改篩選不一樣：改篩選時標註先清掉（篩選器 spec 6.1），因為舊標註判斷的是另一組資料。自動更新時篩選沒變，留著舊標註，電視上才不會每隔幾分鐘就閃一次。
  - `/highlight` 失敗時照現在的規則不標註，卡片上的標註拿掉。
- 分頁在背景（`document.visibilityState` 是 `hidden`）時不更新。回到前景時，如果已經超過間隔就馬上更新一次，沒超過就等到時間到。
- 換儀表板、關掉儀表板或登出時，計時器跟著停掉。
- 預覽不自動更新。
- 檢視者打開之後，擁有者改了間隔，檢視者要重新打開才會用新的間隔。

### 2.3 更新失敗

- 整個 `/data` 失敗（網路斷了、後端重新啟動、回 5xx）：卡片和標註都留著，篩選列旁邊的時間改成警告色的「更新失敗，顯示的是 14:05 的資料」，到下一個間隔再試。成功後換回「最後更新」。
- 只有某幾張卡片的來源載入失敗（`SOURCE_FAILED` 這類卡片層級的錯誤）：照打開時的規則，那張卡片顯示錯誤，其他卡片照常更新。不另外留住那張卡片的舊資料。
- 回 401（工作階段過期）：照現在的規則跳出「登入逾時」（分享 spec 7.10），計時器繼續跑，重新登入後下一次更新就會成功。
- 打開儀表板和改篩選時失敗，照現在的規則顯示錯誤、拿掉格線。有開自動更新的話，到下一個間隔會再試，成功就把格線放回來，電視上的儀表板不會一直停在錯誤畫面。

### 2.4 最後更新時間

- 每份已存的儀表板都顯示，不管有沒有開自動更新。時間是瀏覽器上最近一次成功抓到 `/data` 的時間。
- 格式：今天的寫「14:05」（24 小時制），不是今天的寫「10/6 14:05」。
- 擁有者看到：「最後更新 14:05」，旁邊是間隔下拉選單。
- 其他人看到：有開自動更新時寫「每 5 分鐘自動更新，最後更新 14:05」，沒開時寫「最後更新 14:05」。

### 2.5 後端負擔

- 每次更新等於打開一次儀表板：每個來源載入一次（外部 API 會被打一次），異常檢查拿 `/data` 留著的資料（`DashboardDataService.recent`），不再讀來源。
- 資料沒變時，送給 JEV 的摘要和題目一樣，異常檢查走 LRU 快取，不會再問 JEV。
- 上傳的來源只有按過「更新資料」才會變。自動更新主要是給外部 API 來源，以及會被別人更新的上傳來源。
- 自動更新沒有開出新的 API，沒登入的人本來就能一直重新整理頁面。沒登入的呼叫次數限制是另一項 P2，不在這次範圍。

## 3. 資料格式

`DashboardConfig` 多一個 `refreshMinutes`：

```json
{ "id": "…", "name": "營運總覽", "layout": [ … ], "filters": { … }, "refreshMinutes": 5 }
```

- 只能是 1、5、10、15。沒有這個欄位或是 null，代表不自動更新。
- 其他值回 400「自動更新只能選 1、5、10、15 分鐘」。

## 4. API

- `GET /api/dashboards/{id}`：設定多一個 `refreshMinutes`，沒設就沒有這個欄位。擁有者、被分享的人、沒登入的訪客都拿得到。
- `PUT /api/dashboards/{id}`：body 可以帶 `refreshMinutes`，照第 3 節驗證後存起來。跟 `filters` 一樣是整份取代：前端拖拉版面、移除卡片、存預設篩選、改 KPI 卡時送的是整份設定，`refreshMinutes` 原封不動帶回來；沒帶就是清掉。
- `POST /api/dashboards`（建立）：body 帶了 `refreshMinutes` 也不理，跟 `filters` 一樣。
- `POST /api/dashboards/{id}/charts`（加到既有儀表板）：保留原本的 `refreshMinutes`。
- `/data`、`/highlight` 不變。

## 5. 後端

- `DashboardConfig` 多一個 `Integer refreshMinutes`，放在 `filters` 後面。四個參數的建構子照舊給 null。其他直接呼叫 7 個參數建構子的地方（主程式和測試共 19 處 `new DashboardConfig(`，有些是四個參數的）跟著補一個參數。
- `DashboardRepository.Stored` 多一個 `refreshMinutes`，null 時不寫出來（`config_json` 是 jsonb，不用 migration）。
- 驗證寫在 `DashboardService`（例如 `requireValidRefresh`），由 `update` 呼叫。
- `update` 把 `c.refreshMinutes()` 存起來；`append` 帶著 `current.refreshMinutes()`；`create` 給 null。

## 6. 畫面

### 6.1 篩選列右邊

- 放在篩選列（`DashboardFilters`）右邊、「加 KPI 卡」左邊，由左到右：
  - 時間文字（2.4），`text-caption`、`text-medium-emphasis`。更新失敗時改用警告色（`text-warning`）。
  - 旁邊另外放一個視覺上隱藏的 `role="status"`（`d-sr-only`），只有更新失敗時才有內容。螢幕閱讀器只在更新失敗時讀一次，不會每次更新都讀時間。
  - 擁有者才有：「自動更新」下拉選單（`v-select`，寬約 150px），選項是 2.1 的五個。
- 窄螢幕照篩選列現有的 `flex-wrap` 換行。
- 儀表板沒有任何卡片時，篩選列不顯示（篩選器 spec 6.1），時間和下拉選單跟著不顯示，也不自動更新。

### 6.2 改間隔

- 擁有者選了新的間隔，就用格線上目前的版面、存著的預設篩選（不是臨時的）和新的 `refreshMinutes` 送 `PUT`，跟「存成預設」一樣走 `queueWrite` 排隊。成功後交給 App 換成回傳的設定，走「只少了卡片」的捷徑，不重抓資料。
- 存檔還沒回來時，下拉選單停用；拖拉版面這時也跟 `removing`、`savingFilters` 期間一樣先不存檔。
- 失敗時錯誤顯示在儀表板上面的錯誤區，下拉選單回到存著的值。

### 6.3 計時器

- 放在 `DashboardView`，用一個 `setTimeout`，不用 `setInterval`。每次抓完 `/data`（打開、改篩選、自動更新，成功或失敗都算）之後，從那時重新排下一次。
- 時間到了先排好下一次再抓。這次的回應被丟掉時（例如中途移除卡片，走了不重抓的捷徑），計時也不會斷。
- 同一時間只會有一個計時器。重新排之前先清掉舊的。
- 自動更新照改篩選的流程走：`fetchData(++loadSeq)`，所以舊的回應照樣會被丟掉（防過期的 `loadSeq`）。差別只有 2.2 的標註和 2.3 的失敗處理。
- 卡片還在退場（`leaving`）時，這一次先跳過，退場結束的 `load()` 會自己抓。
- `onBeforeUnmount` 清掉計時器、拿掉 `visibilitychange` 監聽。

## 7. 測試

### 7.1 後端

- `refreshMinutes` 存檔、讀回；1、5、10、15 都收。
- 0、2、30、60、-1 回 400，訊息是第 3 節那句。
- `PUT` 沒帶 `refreshMinutes` 時清掉。
- 加到既有儀表板時保留；建立時帶了也不存。
- 被分享的人、沒登入的訪客 `GET` 拿得到 `refreshMinutes`。

### 7.2 前端

用假的計時器（`vi.useFakeTimers`）：

- `refreshMinutes` 是 5：打開後 5 分鐘再打一次 `/data`，帶著目前臨時改的篩選，接著打 `/highlight`。
- 沒有 `refreshMinutes`：過了 15 分鐘都沒有再打 `/data`。
- 改篩選之後，從改的時候重新計時。
- 分頁在背景時不打；回到前景時已經超過間隔就馬上打。
- 更新時舊的標註留著，新的回來才換。
- 自動更新的 `/data` 失敗：卡片還在，顯示「更新失敗，顯示的是 … 的資料」；下一個間隔再試，成功後換回「最後更新」。
- 卸載之後不再打 API。
- 時間格式：今天、不是今天。
- 擁有者：有下拉選單；選了之後 `PUT` 帶新的 `refreshMinutes` 和存著的預設篩選，不重抓 `/data`。檢視者：沒有下拉選單，看到「每 5 分鐘自動更新，最後更新 …」。
- 預覽不排計時器。

### 7.3 瀏覽器（主 session 自己做）

- 擁有者打開一份用上傳來源的儀表板，看到「最後更新 HH:mm」，間隔改成每 1 分鐘，重新整理頁面後還是每 1 分鐘。
- 臨時選一個篩選，在資料頁對那個來源按「更新資料」選「接在後面」加一份新檔案，回到儀表板等 1 分鐘，數字變了、時間跟著變、篩選還在。
- 用檢視者帳號和沒登入的公開連結各開一次，看到「每 1 分鐘自動更新，最後更新 …」，沒有下拉選單，也會自己更新。
- 停掉後端等一次更新，卡片還在，時間變成「更新失敗」；後端啟動後，下一次更新恢復。
- 自己讀截圖，確認時間和下拉選單在篩選列右邊，390px 寬時換行不疊在一起。

## 9. 不做

- 輪播：多份儀表板輪流顯示在會議室電視上。
- 「立即更新」按鈕。
- 檢視者自己改間隔或暫停。
- 30 分鐘以上的間隔，要先把工作階段的閒置時間拉長或改存資料庫。
- 每張卡片各自的間隔。
- 後端推播（WebSocket、SSE），或後端排程先把資料抓好。
- 只在資料真的變了才換畫面。

## 10. 決定（2026-10-07）

| 題目 | 選擇 | 沒選的 |
|---|---|---|
| 做哪一種 | 自動更新加上顯示最後更新時間（使用者選） | 只自動更新、只顯示時間 |
| 誰設定間隔 | 擁有者設定，存在儀表板（使用者選） | 檢視者可以臨時改、每個檢視者自己設 |
| 排程 | 調到 P2，現在開始（使用者選） | 先不開始、維持 P3 |
| 間隔選項 | 1、5、10、15 分鐘 | 30、60 分鐘（工作階段閒置 30 分鐘就過期） |
| 更新失敗 | 留著舊畫面，寫出「更新失敗」，下一個間隔再試 | 跟打開時一樣拿掉格線顯示錯誤 |
| 更新時的標註 | 留著舊的，新的回來再換 | 跟改篩選一樣先清掉 |
| 背景分頁 | 暫停，回到前景時超過間隔就馬上更新 | 背景也照常更新 |
